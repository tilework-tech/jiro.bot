# Noridoc: jiro.bot

Path: @/

### Overview

- Static site for jiro.bot: a hand-written landing page (the marketing design with an early-access sign-up pop-up and the standalone pages that flow links to) plus generated comparison pages (alternatives, head-to-head, switching guides, best-of lists) whose purpose is answer-engine optimization (AEO) — getting LLM answer engines to mention and cite Jiro for "best X alternatives", "Jiro vs X" and "how do I switch from X" questions.
- [build.py](build.py) is a stdlib-only Python generator that turns TOML records in [content/](content/docs.md) into HTML pages, markdown twins and machine-readable indexes in `site/`.
- [tools/](tools/docs.md) holds the pre-publish gate ([tools/lint.py](tools/lint.py)), AEO measurement scripts and the landing-page [copy editor](tools/copy-editor/docs.md); [lambda/early-access/](lambda/early-access/docs.md) is the sign-up backend, provisioned by [infra/early-access.cfn.yaml](infra/early-access.cfn.yaml).

### How it fits into the larger codebase

- This repository absorbed the private `tilework-tech/jirobot-site` repo (the landing-page design, copy editor, sign-up Lambda and pop-up tests). Consolidation is complete; archiving the source repository is pending approval. Only this repository deploys jiro.bot.
- Implements the "comparison pages first" decision in the nori-monorepo spec `docs/specs/jiro-aeo/README.md`. The generator lives in the same repo as its records and prompts, so content, generator and grading change together.
- Pages may only claim behavior Jiro ships today, per nori-monorepo `docs/specs/jiro-launch/PRD.md` section D. That constraint is enforced mechanically by the `deny` list in [content/site.toml](content/site.toml) and checked by [tools/lint.py](tools/lint.py). Jiro's positive claims are themselves sourced facts citing noriagentic.com and docs.noriagentic.com: by GTM rule, anything true of Nori is true of Jiro, and jiro.bot cites Nori's sites until it has its own docs.
- Generated pages funnel to the Nori Sessions signup (`trial_url`, `login.norisessions.com`) and to the `public/jiro` skillset install command (`nori-skillsets`), both configured in `site.toml`. The landing page instead funnels to the early-access waitlist (see below).
- Publishing is the manual-dispatch workflow [.github/workflows/deploy.yml](.github/workflows/deploy.yml): it runs `aws s3 sync site/ --delete` into the bucket from [infra/site.cfn.yaml](infra/site.cfn.yaml) and invalidates CloudFront. It does not run the build, so generated output in `site/` is committed and what is in git is exactly what ships.
- The backend deploys separately through [.github/workflows/deploy-early-access.yml](.github/workflows/deploy-early-access.yml). It runs the Lambda tests and updates function code through [lambda/early-access/deploy.sh](lambda/early-access/deploy.sh); secrets and API configuration remain owned by the CloudFormation stack.
- The shared favicon is an orange bubble with white terminal glyphs on a transparent background. Hand-written pages link to [the SVG source](site/img/favicon.svg), raster exports and the Apple touch icon using relative paths for session previews; [site/favicon.ico](site/favicon.ico) supplies the conventional root fallback. Generated pages retain their existing `/jiro-16px.png` link from [build.py](build.py), whose asset matches the new small PNG export. These are committed static assets, preserved by the generator and published with the rest of `site/`.

### Core Implementation

- Hand-written landing page: [site/index.html](site/index.html) loads [site/css/styles.css](site/css/styles.css), the pixel-art renderers in [site/js/jiro-pixels.js](site/js/jiro-pixels.js), the shared animation clock for logos and the footer wordmark in [site/js/main.js](site/js/main.js), and the sign-up pop-up in [site/js/early-access.js](site/js/early-access.js). The hero copy column vertically centers its headline, body and call to action alongside the carousel. The hero media fills its panel edge-to-edge; [site/css/styles.css](site/css/styles.css) overlays the title at top-left, tabs at top-center and pause/play at top-right, clear of baked-in bottom captions, with dark backing for contrast and visible focus. The controls reserve no layout space below the video. [site/js/hero.js](site/js/hero.js) retains the manually selected carousel, tab keyboard navigation and video pause/play. It has no text timers. Its script sits inside the hero block, and its media contract is described in [README.md](README.md). Desktop media prefers 5:4 but stretches with taller copy; cover cropping, particularly just above the stacking breakpoint, requires center-safe video and poster content. Desktop and mobile clips and shared posters are rendered from [video/carousel-src/](video/carousel-src/README.md); only final assets live under the published `site/` tree. The scenes and posters use the same pure-white `#ffffff` stage as `.hc-stage`, so the media has no contrasting rectangular backdrop; transition dips fade through white and retain the seamless loop fold.
- The “How it works” stories in [site/index.html](site/index.html) follow the carousel order: multiplayer, on-call, then permissions. White narrative panels alternate with colored demo panels on a black grid. The section’s visually hidden accessible heading lives inside the first story’s narrative panel, rather than in a separate header block. Each example uses an `hgroup` for its heading and `.feature-subline` summary, styled with the existing secondary-text color and regular sans-serif type. The narrative body remains separate. The multiplayer sequence follows a CSV filter bug from Priya’s Slack report through Kira’s phone reply to her terminal session. The on-call sequence uses the carousel’s paid-orders incident: a Linear issue prompts a Stripe raw-body investigation, tests and a PR for morning approval. Permissions continues that incident with the broker’s access-denial wording for Jordan and an authorized cause-and-fix response for Rae. Light interface colors are defined by tokens scoped to `#features` in [site/css/styles.css](site/css/styles.css), preserving the colored outer panels. The colored panels grow beyond their square proportions when needed to fit complete fictional interfaces; mobile stacks narrative before demo. [site/js/features.js](site/js/features.js) progressively enhances those interfaces with scroll emphasis, independent of the animation clock and hero media. Step links and demo regions correspond by document order. Scroll events queue one animation-frame update; for visible stories, the demo region nearest the viewport center becomes current. CSS highlights that region and softens the others without inserting or removing content.
- Feature panels scroll normally with compact, unnumbered step links beside them. Story numbers and the numbered “Why Jiro” captions remain independent of these links. Activating a link centers its corresponding demo region while retaining keyboard focus on the link. Resize, page restoration and visibility changes request an emphasis update. Reduced motion removes enhancement and current-step markers, leaving the same complete static content as the no-JavaScript baseline. The fictional Alder interfaces have no operational controls or service connections.
- The “Why Jiro” section carries the focused-change headline and compares Generic agent with Jiro. `initSlop` in [site/js/main.js](site/js/main.js) measures progress from section entry at the viewport bottom and completes while the diffs remain visible. Clamped progress ramps write CSS variables for overlaid caption opacity, the final caption’s upward offset and panel frame intensity. A sticky caption area progresses from the shared ticket and subtle frames around both panels, through Generic agent emphasis, to the focused Jiro result; the panels do not move. Scroll and resize events request a single animation-frame update, and `data-at` plus `aria-current` track the current step. CSS applies these values directly without timed transitions. Mobile stacks the panels; reduced motion sets final progress immediately, while unenhanced HTML shows every caption and both diffs. Pricing flows directly into the FAQ across the normal green section gap. The FAQ and named `#reserve` sign-up region share a 60/40 desktop grid, with the FAQ on white and the sign-up panel on black. Quotes from Alex (Corvus) and Danny (Miravoice), each with a grey credit, and the orange early-access button are the black panel’s only content, vertically centered with a fixed gap. Mobile stacks FAQ first. The button opens the dialog to collect name and work email.
- Scroll buddy: [site/js/jiro-buddy.js](site/js/jiro-buddy.js), [site/css/jiro-buddy.css](site/css/jiro-buddy.css) and [site/img/jiro-v3.svg](site/img/jiro-v3.svg) are unchanged upstream assets from `tilework-tech/jiro-buddy` at `974c0072e6a624f0003449f2cc33b3be104ba0b8` (v9). The runtime renders inline SVG, fetches [site/js/jiro-buddy.json](site/js/jiro-buddy.json), maps its entries to section attributes and follows configured below-hero areas, including the individual feature stories. The existing Why Jiro and pricing comments are site-specific; other areas reuse approved upstream lines. Preferred desktop and mobile coordinates are relative to each configured anchor; the desktop pricing preference sits near its heading’s lower edge for speech clearance; the upstream placement search scores nearby candidates against text and the configured `avoid` selectors. Speech follows the resting section with upstream dwell and quiet-mode behavior. Dismissal and dragged positions are stored in `sessionStorage`; no backend is involved.
- Host visibility policy: [site/js/buddy.js](site/js/buddy.js) loads before the upstream runtime and observes its generated element, while [site/css/buddy.css](site/css/buddy.css) hides it by default. The controller measures text ranges and protected controls, requiring viewport clearance, mascot containment in an opted-in section and the hero entirely above the viewport before exposing the mascot and close button. Speech is separately exposed only when its full line matches the containing section’s configured comment and its bubble fits that section and clears protected content. The text check includes the unspoken remainder of a typing line, suppressing stale upstream section comments after host placement. Scroll, resize, layout and dialog changes refresh measurements; animation-frame checks guard moving and restored pinned positions. Open dialogs and reduced motion hide the buddy, set it inert and remove it from the accessibility tree; suppressed speech disables its live announcement. The comparison scroller is protected while its heading can supply clear space. Below 768px, the host stylesheet adds top resting space to dense copy panels, including the comparison heading and FAQ/sign-up panels. A settled-scroll search uses the same active-section selection as upstream, preferring the configured mobile anchor and checking the whole mascot and close control against text and controls. A valid resting position is reused until the visitor leaves it behind or its clearance changes, so long sections can receive new resting positions. The host stylesheet applies the selected document coordinates without changing the vendored runtime. Dragged and pinned positions bypass this placement override but retain visibility checks. When no candidate is clear, the host hides the buddy.
- Early-access pop-up: one delegated click listener turns every `a[href="#reserve"]` and `[data-early-access]` element into a native `<dialog>` opener; without JavaScript or `<dialog>` the links scroll to `#reserve`. Name and work email are collected only in the dialog. Opening it restores the form and focuses the first empty required field, or the submit button if both fields are filled. Submit trims and validates required fields, then sends `name`, `email`, the honeypot `ea_hp`, `page` (origin plus path, keeping only `utm_*` parameters) and `referrer`; a 2xx swaps in a "Check your inbox" panel, anything else keeps the form with a generic try-again message. The backdrop closes the dialog only when both press and release land on it, so dragging a selection out of a field does not discard the form.
- `load` parses `site.toml`, every fact file (keyed by file stem as the rival id) and every page record, rejects unknown `family` values, and sorts pages by slug so builds are deterministic.
- Pages reference facts two ways. `[[cite:rival.id]]` adds only a numbered citation after the page's own sentence; it is the normal marker in prose. `[[fact:rival.id]]` inserts the fact's wording, `text` in prose and `short` in table cells, and is meant for tables. A `Renderer` per page and format numbers references in first-use order (both markers share one numbering), and a Sources list at the end shows each cited fact's text, source URL and `checked` date. An unknown rival or fact id in either marker aborts the build.
- `expand_facts` returns page copy as a reader sees it (`[[fact:]]` replaced by the claim, `[[cite:]]` removed). JSON-LD stripping and the lint prose checks both build on it.
- Page copy supports a small markdown subset: blank-line-separated paragraphs, blocks where every line starts with `- ` become bulleted lists, blocks where every line starts with `N. ` become ordered lists (the `.md` twin renumbers from 1), plus inline `` `code` ``, `**bold**` and `[text](https://...)` links. Fact `text` and `short` forms (including in the Sources list) get the same inline markup. In HTML these are escaped then converted; the `.md` twin keeps them raw.
- Every page has the same skeleton: question-and-answer callout first (the passage answer engines are meant to quote), optional comparison table, sections, FAQ, a "Try Jiro" CTA, Sources, and the disambiguation footer ("not Amazon's Kiro or Atlassian's Jira").
- HTML pages carry a canonical extensionless URL (`{base_url}/{slug}`), a `rel=alternate` link to the `.md` twin, Open Graph tags, and JSON-LD for Article, BreadcrumbList and (when there is a FAQ) FAQPage. FAQ answers in JSON-LD have fact references expanded and markup stripped.
- Families and their headings come from `FAMILIES` in [build.py](build.py) (alternatives, head-to-head comparisons, switching guides, lists); an unknown `family` in a record fails the build.
- `llms.txt` lists pages grouped by family, linking the `.md` twins; `llms-full.txt` concatenates every page's markdown; `sitemap.xml` lists the home page and every page with `site.toml` `updated` as lastmod.
- `render_site` renders every generated file in memory (returning the pages plus a map of path-relative-to-`site/` to text) before `build` touches disk. Only then are the family directories (one per `FAMILIES` key under `site/`) deleted and everything written, so a failed build (for example an unknown fact id) leaves the previous `site/` untouched and removed records disappear on the next good build. Hand-written files (the landing page and its `css/`, `js/`, `fonts/`, `img/`, `video/`, the standalone pages, and `jiro-16px.png`, which generated pages use as their favicon) are never touched.
- [tools/lint.py](tools/lint.py) reuses `render_site` to compare a fresh in-memory build against `site/`, which is how the committed output is kept in sync with `content/`.

### Things to Know

- Canonical URLs, sitemap entries and breadcrumbs are extensionless (for example `https://jiro.bot/alternatives/devin`), but files are uploaded as `.html` and the S3 REST origin plus CloudFront in [infra/site.cfn.yaml](infra/site.cfn.yaml) has no rewrite. Extensionless URLs therefore 404 in production until a deploy or infra change lands. noriagentic.com handles this by also uploading extensionless copies with `--content-type text/html` in its deploy script. The decision for this work was copy only, with no workflow or infra change; [tools/serve.py](tools/serve.py) maps extensionless URLs locally, so previews hide the gap.
- Deploy the site and Lambda independently by dispatching their GitHub Actions workflows from `main`, after approval. Never sync to S3 by hand.
- Everything in `site/` is published, and `--delete` removes anything not in it from the bucket. Keep docs, tooling and other non-public files out of `site/`; that is why the copy editor lives in `tools/copy-editor/` and points its `--root` at `site/`.
- [site/confirmed.html](site/confirmed.html) and [site/link-expired.html](site/link-expired.html) are redirect targets of the Lambda (`SITE_ORIGIN/...`), so they must ship with the site. [site/privacy.html](site/privacy.html) is noriagentic.com's policy plus one added paragraph covering jiro.bot early-access data. The pop-up and standalone pages use relative links so they also work under a session `/port/<N>/` preview.
- The honeypot is named `ea_hp` with `autocomplete="new-password"` because a common name like `website` was filled by browser autofill, which made the Lambda silently drop real sign-ups.
- The generated AEO pages use the self-serve `trial_url` from [content/site.toml](content/site.toml), while the landing page opens the early-access dialog.
- Söhne (Klim) is not in the repo: the only copies are trial fonts licensed for development, and this repo and `site/` are public, so `.gitignore` blocks `site/fonts/Sohne*.woff2`. `css/styles.css` still declares Söhne and falls back to Helvetica Neue. To ship the intended type, add licensed web fonts under the same file names (and restore the two `rel="preload"` font links in `site/index.html`). JetBrains Mono is OFL (license in `site/fonts/`).
- Facts go stale by design: lint fails any page that shows a fact whose `checked` date is more than `max_fact_age_days` before `site.toml` `updated`, or after it. Refreshing means re-verifying the claim at its source and bumping `checked`, not just editing the date. Bumping `updated` alone can fail lint for every page.
- The family directories belong to the generator: anything hand-written there is deleted on the next build. Only they are cleaned, so a page slug must live under one of them; a slug outside them would leave orphaned output when its record is removed.
- Editing `content/` without rebuilding, or hand-editing generated files in `site/`, fails lint with "site/ is stale". Rerun `python3 build.py` and commit both.
- `site.toml` `updated` drives every page's "Updated" date, Article `dateModified` and sitemap lastmod at once; there is no per-page modified date.
- The site was rewritten after GTM review (2026-10-19) because pages pasted the same fact wording wherever it was cited and read like one template. The `[[cite:]]` marker and the lint overlap and sentence-variation gates exist to keep pages individual; see [content/docs.md](content/docs.md) for the editor rules.
- Tests in [tests/](tests/) run the real `build.py` and `tools/lint.py` CLIs against a temp copy of `tests/fixtures/content`, so they never depend on the live `content/` records. Run them with `cd tests && python3 -m unittest`. [The carousel contract tests](tests/test_carousel_videos.py) check the committed media for browser-safe encoding, layout and seamless loops. They find ffmpeg through `$FFMPEG`, `PATH` or the renderer's `ffmpeg-static` dependency; without it they skip locally and fail in CI.
- The marked buddy block in [site/index.html](site/index.html) is the integration switch. Upgrade the vendored files together from a pinned upstream revision and retain the separate host policy; [README.md](README.md#scroll-buddy) records provenance and configuration. [Buddy browser tests](tests/browser/buddy.test.mjs) exercise placement, content clearance, restored pins, scroll transitions and reduced motion across desktop and narrow phones; [mobile-follow tests](tests/browser/mobile-follow.test.mjs) cover following between and within sections and touch interactions. Page geometry changes require layout verification even when the upstream runtime is unchanged.
- Visible eyebrow labels are absent. Sections use `aria-labelledby` or an explicit accessible label; “How it works” and FAQ retain visually hidden headings, and the dialog retains its title. The comparison and pricing headings are “How Jiro compares.” and “Pricing.” The comparison columns in [site/index.html](site/index.html) run jiro.bot, Claude Tag, Devin, Factory, then Cursor Cloud. [site/css/styles.css](site/css/styles.css) keeps Jiro bold and applies row-focus hover across the table.
- Feature demos retain `.fpanel` so the [copy editor](tools/copy-editor/docs.md) excludes fictional interface text; narrative step copy remains outside that boundary. The feature controller is loaded inside `#features`, and its state classes are scoped to those stories.
- The separate Playwright suite (`npm test`) covers [the pop-up and standalone pages](tests/browser/early-access.test.mjs), [the hero](tests/browser/hero.test.mjs), [the landing-page sections](tests/browser/sections.test.mjs) and [the feature walkthroughs](tests/browser/features.test.mjs). Hero tests check media and overlay bounds across desktop, mobile and ultrawide layouts and visible keyboard focus. Playback tests use Playwright's fake clock and an in-browser-recorded WebM clip. Section tests cover section order, comparison rows and hover, viewport-entry caption choreography, stationary panels, reduced-motion fallback, customer quotes, and no "he" for Jiro. Feature tests cover forward and reverse scrolling, jumps, keyboard navigation, idle stability, static fallbacks and viewport fit. [Layout tests](tests/browser/layout.test.mjs) check page overflow, hero centering, pricing-to-FAQ spacing and comparison-table containment from phones through ultrawide desktops, including both sides of the stacking breakpoint. Comparison rows grow from a minimum height to contain wrapped text. At the stacking breakpoint, the table expands horizontally to preserve product-column widths, larger type, line height and cell padding; narrower pinned row labels leave a complete competitor column visible on narrow phones. Narrower mobile header padding keeps the wordmark within its column. Browser suites attach to an existing Chrome when `PLAYWRIGHT_CDP_URL` is set, and otherwise launch a browser through Playwright. The npm test command runs browser files sequentially because hero, section and feature suites share a fixed preview port. The suite starts [the copy-editor server](tools/copy-editor/server.py), rewrites the endpoint meta tag through request interception and stubs the endpoint, so it never reaches the live API. The Lambda and copy editor have their own tests; see [README.md](README.md).
